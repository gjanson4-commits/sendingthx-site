SMS consent via Stripe Checkout custom fields

A working design for capturing gift-delivery text consent on Stripe-only checkouts — merchants who aren't on Shopify and have no cart-page extension point.

Drafted July 2026
Status: draft, unpublished. This page is intentionally not linked from the site nav or footer and is marked noindex. It exists to work out the design before anything ships. Nothing here has been reviewed against the Twilio compliance checklist yet, and no merchant should implement this until that review happens.

Why this exists

On Shopify, the gift-notification Theme App Extension renders a real checkbox plus phone number field directly on the cart page — full control over layout and consent language, matching Twilio's Consumer-Initiated Viral Messaging example almost exactly.

Stripe Dashboard Apps have no equivalent extension point. A Stripe App only extends the Stripe Dashboard — the merchant's own admin view — not the customer-facing checkout page. For a merchant using Stripe directly (hosted Checkout or a Payment Link, no custom site), there's currently no way to collect this consent at all.

The constraint

Stripe Checkout Sessions support up to 3 custom_fields, each of type text, numeric, or dropdown. There is no native checkbox type in custom_fields. Stripe does have a real checkbox mechanism — consent_collection — but it's purpose-built for Terms of Service acceptance and promotional-email opt-in specifically, not reusable for arbitrary consent language.

Checkout also has no conditional field logic: a field can't be set to "required only if a different field's answer is X." That means the recipient phone field can't be hard-required only when the consent dropdown says yes — it has to stay optional, with copy doing the work instead.

Proposed design

Three fields, using the full allowance:

FieldTypeRequiredPurpose
Text notification consentdropdownYesThe consent action itself. No option is pre-selected — the shopper must actively choose, same bar as an unchecked-by-default checkbox.
Recipient's phonetextNoOnly meaningful if consent = yes. Optional because Checkout can't make it conditionally required.
Personal notetextNoOptional message relayed to the recipient, matching the Shopify block's note field.
Checkout Session custom_fields
"custom_fields": [
  {
    "key": "gift_notify_consent",
    "label": {
      "type": "custom",
      "custom": "Text a delivery notification?"
    },
    "type": "dropdown",
    "dropdown": {
      "options": [
        { "label": "No thanks", "value": "no" },
        { "label": "Yes — I have the recipient's consent to text them", "value": "yes" }
      ]
    },
    "optional": false
  },
  {
    "key": "gift_recipient_phone",
    "label": {
      "type": "custom",
      "custom": "Recipient's phone (only if you said yes above)"
    },
    "type": "text",
    "text": { "maximum_length": 20 },
    "optional": true
  },
  {
    "key": "gift_note",
    "label": {
      "type": "custom",
      "custom": "Personal note for the recipient (optional)"
    },
    "type": "text",
    "text": { "maximum_length": 160 },
    "optional": true
  }
]

Wiring it to the existing API

No new SendingThx infrastructure is needed for this. The merchant already has to write a handler for their own checkout.session.completed webhook (on their own Stripe account, with their own webhook secret — unrelated to the SendingThx-signed requests the Dashboard App itself makes). That handler reads session.custom_fields, and if gift_notify_consent is "yes" and a phone number was entered, calls the existing POST /v1/orders endpoint exactly as documented today — same payload shape, same auth, nothing new to build on our side.

In plain terms: this is a configuration recipe plus a few lines of glue code for the merchant, not a new product surface. The only new SendingThx-side work, if any, would be documentation.

Open items before this can ship

  • Full Twilio compliance review of the dropdown consent language, matching the same bar as the approved Shopify checkbox wording.
  • Decide what happens if a shopper selects "yes" but leaves the phone field blank — merchant-side validation, or silently skip the notification?
  • Test the actual rendered field order and wording in a live Stripe test Checkout Session — nothing here has been verified against the real Dashboard yet.
  • Decide where this guide ultimately lives once finalized — likely as a public technical-documentation page, possibly linked from the Stripe App Marketplace listing.
